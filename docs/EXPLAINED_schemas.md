# EXPLAINED: backend/schemas.py

> **One-line summary:** This file defines the shapes of data that travel in and out of your API — what a request body must look like, and what a response will always contain.

---

## What Pydantic Is and Why It Matters

Before reading this file, you need to understand **Pydantic**.

Python is a dynamically typed language — you can put anything in any variable. This is flexible but dangerous: if your endpoint expects `case_type` to be a string but someone sends an integer, Python won't catch it and you'll get a confusing crash deep in your code.

**Pydantic fixes this.** When you define a Pydantic model:
1. FastAPI automatically parses the incoming JSON into that model.
2. If any field is the wrong type or missing, FastAPI returns a 422 error *before your code even runs*.
3. When you return a model from an endpoint, FastAPI automatically serializes it to JSON.

This means your endpoint functions never need to call `json.loads()` or do type checking — Pydantic handles all of it.

## Section-by-Section Walkthrough

### Imports

```python
from pydantic import BaseModel, ConfigDict
from typing import List, Optional, Any
from datetime import datetime
```

- `BaseModel` — every schema class inherits from this. It's what makes a class "Pydantic."
- `ConfigDict` — configuration for how the model behaves (see below).
- `Optional[str]` — means "string or None." Equivalent to `str | None` in Python 3.10+.
- `Any` — means "accept anything." Used in `StandardResponse.data` because different endpoints return different data types.

---

### The Base/Create/Response Pattern

Every major resource (User, Case, Document) follows the same three-class pattern:

```python
class DocumentBase(BaseModel):    # ← shared fields
    file_type: str
    capture_metadata: Optional[str] = None

class DocumentCreate(DocumentBase):  # ← what the client sends
    pass

class Document(DocumentBase):     # ← what the server returns
    id: int
    case_id: int
    file_hash: str
    created_at: datetime
    model_config = ConfigDict(from_attributes=True)
```

**Why three classes instead of one?**

- **Base** holds fields that are both sent by clients AND returned by the server. Avoids repetition.
- **Create** is what the client sends when creating something. It never includes `id` or `created_at` — those are generated by the server, not provided by the client.
- **Response** (named after the resource: `Document`, `Case`, `User`) is what the server returns. It includes everything in Base plus server-generated fields like `id`, `created_at`, `file_hash`.

If you put `id` in `DocumentCreate`, clients could try to specify their own IDs — a security hole. This pattern prevents that.

---

### `model_config = ConfigDict(from_attributes=True)`

This appears on every "response" class (Document, Case, User).

**What it does:** Allows Pydantic to read data from SQLAlchemy model objects (which use attribute access like `document.file_hash`) rather than only from dicts.

Without this, when you do:
```python
@app.get("/documents/{id}", response_model=schemas.Document)
def get_document(id: int, db: Session = Depends(get_db)):
    return db.query(models.Document).filter(models.Document.id == id).first()
    # ↑ This is a SQLAlchemy ORM object, not a dict
```
Pydantic would crash because it can't find dict keys on an ORM object. With `from_attributes=True`, it uses `obj.field_name` instead of `obj["field_name"]`, which works on ORM objects.

**Old name:** In Pydantic v1, this was `class Config: orm_mode = True`. Pydantic v2 renamed it to `ConfigDict(from_attributes=True)`. If you ever see `orm_mode`, it's the same thing — old code.

### RAG Schemas

```python
class SectionInput(BaseModel):
    section_number: str
    act_name: str
    section_title: str
    text: str

class QueryRequest(BaseModel):
    question: str

class QueryResponse(BaseModel):
    answer: str
    citations: List[str]
    hallucination_flags: List[str]
    retrieved_sections: List[dict]
```

These are used by the RAG pipeline (`POST /rag/add-section` and `POST /rag/query`).

**`SectionInput`:** What you send when adding a law section to the knowledge base. All four fields are required — if you omit `act_name`, FastAPI returns a 422 error automatically.

**`QueryResponse`:**
- `citations`: section numbers Gemini mentioned in its answer (e.g., `["Section 85", "Section 103"]`)
- `hallucination_flags`: citations that Gemini mentioned but that don't exist in ChromaDB — a sign of hallucination
- `retrieved_sections`: the raw sections ChromaDB returned (so the frontend can show "these sources were used")

### StandardResponse

```python
class StandardResponse(BaseModel):
    success: bool
    data: Any = None
    error: Optional[str] = None
```

This is the **envelope pattern**. Instead of different endpoints returning different JSON shapes, most endpoints return this consistent wrapper. The frontend always knows:
- `response.success` tells you if it worked
- `response.data` has the payload if it worked
- `response.error` has the message if it didn't

**Why this is useful:** Without this, your frontend code would need different logic for every endpoint. With it: `if response.success: show(response.data) else: showError(response.error)`.

### Inconsistency Schemas

```python
class InconsistencyBase(BaseModel):
    case_id: int
    doc_a_id: int
    doc_b_id: int
    contradiction_type: str
    severity: str
    explanation: str

class InconsistencyCreate(InconsistencyBase):
    pass

class Inconsistency(InconsistencyBase):
    id: int
    created_at: datetime
    model_config = ConfigDict(from_attributes=True)
```

These are for **storing** inconsistencies in the database (the `inconsistencies` table in `models.py`). They are separate from the pipeline-internal schemas in `modules/inconsistency/schemas.py` which track the step-by-step Gemini pipeline output.

**Don't confuse:**
- `schemas.Inconsistency` → database storage shape
- `modules/inconsistency/schemas.InconsistencyReport` → full pipeline output with exact quotes

## What Breaks If This File Is Removed

Every endpoint that uses `schemas.X` types would fail at import time with `ImportError`. Since `main.py` imports schemas at the top level, the entire server would fail to start.
